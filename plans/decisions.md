# Decisions Log

Reverse-chronological record of architecture decisions for **Sahayak**.

| Date | Decision | Rationale |
|---|---|---|
| 2026 | **Single shared Neon Postgres; the local instances are gone.** `DATABASE_URL` and `DATABASE_URL_TEST` must resolve to different databases. | One database for the team and the demo. The test database is a separate Neon branch because tests truncate every table, and with no local instance there is no safe fallback to catch a mistake — so `vitest.config.ts` refuses to run if the two URLs collide, and `pool.ts` no longer falls back to `DATABASE_URL`. `db:reset` and `db:seed:fresh` are refused unless `SAHAYAK_ALLOW_DESTRUCTIVE=1`. Tests no longer create/drop a database: a transaction pool cannot, and Neon has no `postgres` database to connect to. See `pg-db-connection.md`. |
| 2026 | **The Firestore mirror is removed** (Postgres -> Firestore outbox, sync service, backfill, CLI, redaction and its two test files, ~1,400 lines). Push is not implemented either; `sendPush` is a logging stub. | The mirror could not deliver anything: its Firestore database was never created, and no client can read the replica because there is no Firebase auth bridge. Meanwhile its seven triggers fired on every write to `users`, `user_verifications`, both profile tables, `help_requests`, `emergency_events` and `request_declines`, and with the drain off the outbox grew without bound — a real cost on a shared database. Removed on 2026-09-27; recoverable in the preceding commit. Neon was never migrated, so it needs no down-migration. Note for the future: deleting a migration file leaves its triggers installed on any database where it had already run. |
| 2026 | **Push (FCM) is not implemented.** `sendPush` logs instead of delivering; the `firebase-admin` dependency and its credential config are gone. The `fcm_token` columns and the call sites that populate them are left in place, so re-enabling push is a matter of restoring a sender behind `push.ts`. | Delivery is email-only for now. Removing the `fcm_token` plumbing would touch registration, users, matching and the police modules, which is a wider change than de-scoping the delivery itself. |
| 2026 | **`logger.error` now serialises `Error` properly.** | `JSON.stringify(new Error(...))` is `{}` because `message` and `stack` are non-enumerable, so every logged error was unreadable — including the guards that refuse to drop the shared database, where reading the message is the entire point. |
| 2026 | **Police directory routes added: `GET /police/seniors`, `GET /police/seniors/:id`, `GET /police/volunteers/:id`.** All police-only, keyset-paginated. | The console's Seniors and Volunteer Detail pages had no data source. `src/modules/seniors/` was an empty directory. Assignment history is derived from `help_requests.dispatch_batch` JSONB via `jsonb_array_elements` because dispatch already records who was offered what — there is no join table to read. Detail in `web-portal-gaps.md`. |
| 2026 | **`senior_profiles.aadhaar_number` is never returned to the police console.** | A government identifier the console has no use for. Returning it would only widen the blast radius of a stolen police session. Enforced by a test that greps the whole response body. |
| 2026 | **A `role='senior'` user with no `senior_profiles` row is listed, not hidden.** | That is the window between approval and completing the registration form, and the approval queue needs to see exactly that person — hiding them makes them unreviewable. |
| 2026 | **The police console shows no volunteer distance, and labels a stale position `(stale)`.** | `base_*` is whatever the volunteer typed at registration, often only a locality, and `current_*` only exists once live position updates ship. A distance column next to a locality-level coordinate is false precision. The server's `can_assign` is the column that matters. |
| 2026 | **Monitoring and Map pages were deliberately not built.** | Monitoring has no defined purpose anywhere in the plans — live status board, system health and dispatch telemetry are three different products, and a guessed API contract is harder to unpick than a missing page. Map needs no backend route (coordinates already ride along on `/police/requests` and `/police/emergency-events`) but does need a mapping-library dependency, which is a decision, not a bug fix. |
| 2026 | **Enqueue via `AFTER INSERT/UPDATE/DELETE` trigger rather than service-level calls**, across 7 business tables. | Writes to these tables span 13 modules; a hand-maintained call list would eventually miss one, and the resulting bug is a replica that is quietly wrong with no error anywhere. A trigger cannot be forgotten. `audit_logs`, `otp_codes`, `otp_attempts`, `refresh_tokens` are excluded as high-churn, short-lived, and (for OTPs) unsafe to replicate. |
| 2026 | **Deletes win over upserts when a batch collapses repeats of the same row.** | A row updated then deleted within one drain window must not be resurrected by the later-arriving upsert. |
| 2026 | **The drain re-reads current row state from Postgres instead of trusting trigger-captured data.** A row deleted between enqueue and drain is treated as resolved, not retried. | Intermediate states are wasted writes, and re-reading is self-healing. Treating a vanished row as resolved avoids retrying it every tick until it was dead-lettered as if it had failed. |
| 2026 | **R-01/R-02 accept an optional `fcm_token` in the body**, persisted to both `user_verifications.fcm_token` and `users.fcm_token`. | A pre-approval account has `role = NULL` and therefore cannot call A-06 (role-gated); the device token must be captured with the registration form. A-06 remains for post-approval refreshes. |
| 2026 | **`dispatch_batch` stores objects `{id, latitude, longitude, distance_m}`, not a bare volunteer-ID array.** The coordinates are the volunteer's fresh-else-base position read at *dispatch* time. Supersedes the earlier "snapshotted on accept" decision below. Q-04 membership is checked with `jsonb_array_elements(e)->>'id'`. | Preserves distance history for later police/volunteer views and makes the batch self-describing; still trivially filterable. |
| 2026 | **Role-filtered reads (Q-03 etc.) answer 404 when the caller has no relationship to the resource** (no existence leak); Q-08 keeps the spec's explicit 403. | Consistent 404-on-hide avoids probing; BR-08 remains explicit for contact exposure. |
| 2026 | **BG-01 excludes already-tried volunteers from re-dispatch batches** and FCMs only the new batch; sweep audits use `actor_id = NULL`. | Avoids re-notifying volunteers who already declined/ignored a dispatch. |
| 2026 | **P-02 supports `actor_id=null` in the query string** to filter system-generated events. | Query params can't express NULL otherwise. |
| 2026 | **Email columns are `text` with a case-insensitive unique index instead of `citext`.** The app lowercases every email at the boundary. | The dev environment's PostgreSQL lacks the `citext` contrib extension and there's no root to install `postgresql18-contrib`; using `text` + `lower(email)` unique index keeps behavior identical without the extension. |
| 2026 | **Dev notif-DPL-01: SMTP optional in development, required in production.** `NODE_ENV=production` fails fast if `SMTP_*` is missing (FCM no longer gates production, since push is not shipping); in development the notification adapters log-and-continue. | Deviates from spec §8 so a bare `DATABASE_URL` is enough to run and test the whole flow on a machine with no mail/FCM credentials. Flagged in `architecture.md`. |
| 2026 | **DB layer: node-postgres + node-pg-migrate.** Raw SQL for conditional `UPDATE … RETURNING`, partial unique indexes, CHECK constraints, and Haversine. No ORM abstraction. | Spec is SQL-centric (Q-05 atomic accept, JSONB, per-senior partial index). |
| 2026 | **Enum-like columns are `text` + CHECK, not PG enum types.** | CHECKs are trivial to evolve in migrations and behave identically for our read/write patterns. |
| 2026 | **OTP codes: bcrypt-hashed, single-use, 10 min TTL.** Issuance limited 3 / email / 10 min (DB-backed count of recent `otp_codes`); verification attempts 5 / email / 10 min via `otp_attempts` (restart-safe). Per-IP request limit uses an in-memory store (loss on restart acceptable). | BR-07. DB-backed email limits survive restarts; IP limit is best-effort. |
| 2026 | **Access token 15 min; refresh 90 days with rotation + family revocation.** Presented token is consumed; reuse of a consumed token revokes the whole family → 401. Raw refresh tokens stored only as SHA-256 hashes. Police sessions: 8 h single access token, no refresh. | A-03 contract; reuse detection requires the chain bookkeeping. |
| 2026 | **`verification_status` is derived, not stored.** Computed from `user_verifications` (PENDING/APPROVED/REJECTED or NONE) for `/me` and A-02. | Single source of truth; no denormalized column to drift. |
| 2026 | **Q-01 returns `status: "PENDING"` and matching runs synchronously in the same request.** | Spec §4 Q-01: "status = PENDING, then synchronously runs matching" while returning the PENDING envelope. Rows committed; FCM fire-and-forget, never awaited. |
| 2026 | **Match distance uses `current_*` when fresh (< 10 min) else `base_*`**, computed with Haversine in SQL (COALESCE per coordinate), bbox prefilter for cheap candidate reduction. PostGIS out of scope. | Spec §6. |
| 2026 | **Background jobs run in-process (node-cron)** with an overlapping-tick lock and `NODE_ENV === 'test'` disablement. No separate worker/queue for this build. | Spec §7; keeps deployment single-process. |
| 2026 | **Volunteer live position was originally planned to be snapshotted onto the request on accept; this was superseded by the dispatch-time `dispatch_batch` object decision above.** | Preserves the correct distance history for later views. |
| 2026 | **Tests: vitest + supertest against a real Postgres test database**, created in global setup and reset between suites. Unit tests where no DB is needed. | Matches chosen toolchain; exercises transactions and constraints for real. |
| 2026 | **Voice agent boundary (Phase 1): the agent holds no backend credential.** The Flutter app verifies the agent's JWT (signature/expiry/`role==='senior'`) and submits requests/emergencies itself. No service-credential middleware built now. | Spec §1; keeps agent read/write-free. |
| 2026 | **Build scope: backend API only.** Police portal React UI (`web/`), Flutter app, and voice agent service deferred; their contracts are defined in `api-plan.md` / `architecture.md`. | User decision; single-process backend is the immediate deliverable. |
| 2026 | **Express 5 + TypeScript (ESM/NodeNext) monolith**; domain-module layout under `backend/src/modules/*`. | Scaffold already in place; matches `scaffolding.md`. |
